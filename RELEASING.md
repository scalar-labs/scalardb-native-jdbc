# Releasing

A release publishes two things from one tag: the driver to Maven Central, and `snsql` and the tools to
the GitHub release, with the release notes from `.changes/`. Everything is under the Apache License
2.0. [release.yml](.github/workflows/release.yml) does both; nothing has been released yet.

## What gets published

| Artifact | Where | Consumed by |
| --- | --- | --- |
| The driver | `com.scalar-labs:scalardb-native-jdbc` on Maven Central | Applications, through Maven or Gradle |
| `snsql` | `scalardb-native-shell-<version>.zip` on the GitHub release | People working at a terminal |
| The tools | `scalardb-native-tools-<version>.zip` on the GitHub release | Operators setting tables up |
| Snapshots of the driver | `<version>-SNAPSHOT` in the Central snapshot repository | Tracking a line between releases |

The samples and the driver's test fixtures are not published. The driver's POM brings JSQLParser and
slf4j-api; the vendor driver is the application's own.

## Versioning

The driver version mirrors the ScalarDB line it is certified against: `3.20.0`, `3.20.1`, and so
on, where the major and minor say "certified against ScalarDB 3.20.x" and the patch is the driver's
own numbering. Certification is per ScalarDB line, not per patch: patch releases
do not change the storage format or the protocol, so the tests run against the newest patch of the
line. A new ScalarDB minor or major gets its own certification run and its own row in the README's
compatibility table.

## Branching model

Every branch except `main` is named after the version it carries, following the same model as
[ScalarDB](https://github.com/scalar-labs/scalardb). Releases are cut from minor version branches,
never from `main`. Branch names carry no prefix, `3.20`; the workflows match them with the `[0-9]+`
and `[0-9]+.[0-9]+` patterns, so a name like `release/3.20` gets no CI and publishes no snapshot.

Fixes land on the newest branch that needs them and are backported down the lines they apply to, by
cherry-pick ([auto-pr.yml](.github/workflows/auto-pr.yml) opens the pull requests for a merged pull
request with a `ScalarDB <version>` project attached). Version branches never merge back.

### Cutting a branch

Bump the parent (`main`) to its next snapshot version first (`4.0.0-SNAPSHOT` when `3.20` is cut),
then cut the new branch from the commit just before the bump. Cutting first would leave both
branches carrying the same version, and each would publish its own build under that one snapshot
version:

```bash
# after the bump has landed on main
git switch main && git pull
git switch -c 3.20 <bump-commit>~1 && git push -u origin 3.20
```

Then, on `main`, copy the `github-actions` entry in [.github/dependabot.yml](.github/dependabot.yml)
with `target-branch: "3.20"` added, since Dependabot reads the file from the default branch only and
workflow files drift between lines. Delete the copy when the line reaches end of life.

## Certifying a line

Set `scalardb` in `gradle/libs.versions.toml` to the newest patch of the line and run the full check
on all five engines (`./gradlew check`; CONTRIBUTING.md for the engine flags), and the
[Isolation](.github/workflows/isolation.yml) workflow on the branch. A release is cut only from a
commit that passed both.

**3.20.0 is the exception: its tests run on ScalarDB 3.19.1.** ScalarDB 3.20.0 removed the
application-level two-phase commit API (`TwoPhaseCommitTransaction` and its manager) that the
integration tests use to hold a ScalarDB transaction prepared, which is how they put rows in flight;
3.20's `GlobalTransactionManager` prepares only inside `commit()`. The transaction metadata columns
and states are the same in both (`Attribute` and `TransactionState` are identical in the 3.19.1 and
3.20.0 jars), so the README and the release notes say "tested against ScalarDB 3.19.1", not
certified against 3.20. Moving the tests to 3.20 is open; until it is done, a 3.20.x release keeps
this exception and says so in its notes.

`release.yml` runs the whole of [CI](.github/workflows/ci.yml) again on the tagged commit, all six
engine configurations included, before it uploads anything. It does not run the isolation tests,
which take about an hour per engine.

## Changelog

The same process as [ScalarDB Saga](https://github.com/scalar-labs/scalardb-saga/blob/main/RELEASING.md#changelog)
and the ScalarDB PostgreSQL frontend, with one difference, under [When releasing](#when-releasing).
[CHANGELOG.md](CHANGELOG.md) and each GitHub release's notes are generated by
[changie](https://changie.dev) (`brew install changie`, `go install github.com/miniscruff/changie@latest`,
or `npm i -g changie`) from one entry file per change, configured in [.changie.yaml](.changie.yaml).
An entry is a file of its own, never an edit to `CHANGELOG.md`, because a backport is a cherry-pick: a
new file always applies cleanly to a release line, while an edit to `CHANGELOG.md` either conflicts
there or applies cleanly into a section that line has already released.

### Adding an entry

A change that users can see adds an entry in the same commit. Run this in the repository and commit
the file it writes:

```console
$ changie new
Kind: Bug fixes
Body: `scalardb-native-tools check` now names the table whose setup is incomplete.
Pull request number:
```

The same without prompts, as an agent runs it:

```bash
changie new --interactive=false --kind bugfix \
  --body '`scalardb-native-tools check` now names the table whose setup is incomplete.'
```

That writes `.changes/unreleased/bugfix-<timestamp>.yaml`:

```yaml
kind: bugfix
body: '`scalardb-native-tools check` now names the table whose setup is incomplete.'
time: 2026-10-29T14:30:05.123456+09:00
```

- **Kind** is `enhancement` (Enhancements: a new capability), `improvement` (Improvements: a change
  to existing behavior, a performance gain included) or `bugfix` (Bug fixes). A change that is two
  kinds gets two entries.
- **Body** says what users see, not how the code changed, following the
  [Guidelines for Writing Release Notes](https://developers.scalar-labs.com/docs/style-guide/release-notes/).
  Start it with `[BREAKING]` when users have to change their code, configuration, or deployment.
  Name a file as code (`docs/errors.md`) rather than linking it: a relative link breaks in the GitHub
  release.
- **PR**, the pull request number, is rendered as a link after the body. Leave it empty for a commit
  pushed directly.

A change users cannot see the effect of (a refactor, tests, benchmarks, CI, the design notes) adds no
entry. A backport needs nothing: the cherry-pick carries the entry file to the release line.

Changes are pushed to `main` directly for now, so nothing checks for an entry before it lands; a
malformed one fails `changie batch` at release. The [Changelog](.github/workflows/changelog.yml)
workflow already runs on every pull request: it fails one that adds no entry and is not labelled
`no-changelog` (Dependabot's are exempt), and any pull request while a pending entry is malformed.
Titles here do not follow Conventional Commits, so unlike Saga's it cannot tell a user-facing pull
request from its title. Once changes go through pull requests, create the `no-changelog` label and
make `entry` a required status check on `main` and the version branches. Not before: a required
check also refuses a direct push.

### When releasing

`changie batch` moves the pending entries into `.changes/v<version>.md` and deletes them, and
`changie merge` rebuilds `CHANGELOG.md` from the per-version files. Between the two, edit
`.changes/v<version>.md` into release notes: the entries were written one change at a time, so
combine those that describe one change and reword them to read as a whole.

Unlike Saga and the PostgreSQL frontend, **every tag is batched, a pre-release included**. Their
pre-releases are rehearsals that preview the next release's notes; a pre-release here, such as
`3.21.0-rc.1`, is a version on Central that users may depend on, so it has notes of its own, and the
release after it lists what changed since.

- **The first release of a line**, `3.20.0`, batches on `main`, before the branch is cut, so
  that the cut takes the batch along and `main` starts the next line with nothing pending.
- **Every later release of the line**, `3.20.1`, `3.20.2`, batches on its release
  branch, in the commit that sets the version. It collects only what was cherry-picked. `main` keeps
  its own copies of those entries, so the next line's first release lists those fixes too, which is
  right for anyone upgrading from the previous line.

`verify-version` refuses a tag, before anything is published, unless `.changes/v<version>.md` exists,
lists at least one change, and no entry is left in `.changes/unreleased/`. The GitHub release takes
that file as its notes.

An entry left pending ships in the tagged release, so it belongs in that release's notes. It happens
when a fix reaches the release branch after the batch. `changie batch` refuses a version it has
already written, so fold the entries in by hand, on the release branch:

```bash
changie batch v<version> --dry-run   # prints the pending entries; nothing changes
# copy those bullets under their headings in .changes/v<version>.md
git rm .changes/unreleased/*.yaml
changie merge
git commit -am "Release notes: the entries left pending folded into v<version>" && git push
```

For the first release of a line, whose batch ran on `main`, delete the same entry files on `main`
too, and copy the edited `.changes/v<version>.md` there. Otherwise `main` keeps them pending, and the
next line's first release lists them again.

Then move the tag to the new commit. Nothing was published from the refused one, since
`verify-version` runs before every other job, so it can simply be deleted and pushed again:

```bash
git tag -d v<version> && git push --delete origin v<version>
git switch <release-branch> && git pull
git tag -a v<version> -m "ScalarDB Native JDBC <version>" && git push origin v<version>
```

## Cutting a release

`release.yml` runs on a `v<major>.<minor>.<patch>` tag, with or without a pre-release suffix. It
refuses a tag that does not match `gradle.properties`, a `-SNAPSHOT` version, a commit that is not on
the tag's minor version branch (`3.20` for `v3.20.0`), and release notes that are missing or incomplete (see [When releasing](#when-releasing)). It then runs CI on the tagged commit, uploads the
driver to the Central Portal for someone to release, and creates the GitHub release with the notes
and the two zips. A pre-release is marked as one and never takes the *Latest* badge.

### Steps

For `3.20.0`:

1. Certify the line, above.
2. Batch the notes: `changie batch v3.20.0`, edit `.changes/v3.20.0.md` into release
   notes, `changie merge`. For the first release of a line this is on `main`, then bump `main` and cut
   `3.20` as in [Cutting a branch](#cutting-a-branch). For a later release it is on `3.20`, in the
   next step's commit.
3. On `3.20`, make the release commit: `version=3.20.0` in `gradle.properties`. Check that
   `.changes/v3.20.0.md` carries today's date, which is the date `changie batch` ran; correct
   it and run `changie merge` if not. Push it and wait for CI.
4. Tag that commit and push the tag:

   ```bash
   git tag -a v3.20.0 -m "ScalarDB Native JDBC 3.20.0"
   git push origin v3.20.0
   ```

5. When `release.yml` has finished, open the deployment on the
   [Central Portal](https://central.sonatype.com/publishing/deployments). Once it has passed
   validation, check the files and select **Publish**. A published version cannot be replaced or
   withdrawn, which is why the workflow never publishes it itself. It takes a while to appear on
   `repo1.maven.org`. The GitHub release exists already, so do not leave a validated deployment
   unpublished. To abandon a release instead, select **Drop**, then delete the GitHub release and the
   tag.
6. On `3.20`, bump `version` to `3.20.1-SNAPSHOT` and push, so that later snapshots from the
   branch do not reuse the released version.

To re-run a release whose tag exists, for example after the upload failed, run `release.yml` by
`workflow_dispatch` with the tag selected as the ref. If only `github-release` failed, use **Re-run
failed jobs** on that run instead: a new run uploads again first, which Central refuses for a version
it already has, and `github-release` would never be reached. A re-run leaves an existing GitHub
release's notes as they are and attaches only the zips it lacks.

## Snapshots

Every commit on `main` and on each version branch publishes the driver's `-SNAPSHOT` to the Central
snapshot repository ([release-snapshot.yml](.github/workflows/release-snapshot.yml)), after the
driver's unit tests and static checks pass. A version branch publishes only a version on its own line
(`3.20` publishes `3.20.*`), so a branch just cut and still carrying `main`'s version cannot overwrite
`main`'s snapshot; that check cannot tell the two apart while they carry the same version, which is
why [Cutting a branch](#cutting-a-branch) bumps the parent first. The Central Portal must have
snapshots enabled for the `com.scalar-labs` namespace, as it does for Saga's. Consumers add the
repository `https://central.sonatype.com/repository/maven-snapshots/`.

## Credentials

The publishing jobs read four secrets, the same ones ScalarDB, ScalarDB Saga and the PostgreSQL
frontend use:

| Secret | What it is |
| --- | --- |
| `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD` | A Central Portal user token for the `com.scalar-labs` namespace |
| `MAVEN_CENTRAL_GPG_SECRET_KEY` | The ASCII-armored private key that signs the artifacts |
| `MAVEN_CENTRAL_GPG_PASSPHRASE` | Its passphrase |

Central checks the signature against the public key on a keyserver, so a key that is not there fails
validation at the Portal, after the workflow has gone green. Saga's
[Publishing the public key](https://github.com/scalar-labs/scalardb-saga/blob/main/RELEASING.md#publishing-the-public-key)
says how to check it. Any branch's workflows can read the secrets; scoping them to `main` and the
tags takes an environment, as Saga's
[Repository settings](https://github.com/scalar-labs/scalardb-saga/blob/main/RELEASING.md#repository-settings)
describe, with `environment:` added to the publishing jobs here.

A local `./gradlew publishToMavenLocal` needs none of them and publishes unsigned.

## Before the first release

Nothing in `publish-maven` or `github-release` has run yet, and the first release is the worst one
to find a mistake with, because it cannot be taken back. Rehearse on a scratch `0.0` branch, as
[Saga's rehearsal](https://github.com/scalar-labs/scalardb-saga/blob/main/RELEASING.md#rehearsing-the-pipeline)
does, in three rungs that each leave more behind than the last:

1. **Guards only.** Before the secrets are granted to this repository, push the branch with
   `version=0.0.1-rc.1`, a batched `.changes/v0.0.1-rc.1.md`, and the tag `v0.0.1-rc.1`.
   `verify-version` and CI run for real, and
   `publish-maven` stops at its secrets check, so nothing is published. Check first that the
   `MAVEN_CENTRAL_*` secrets do not already reach this repository from the organization: if they
   do, this rung uploads a deployment, which then has to be dropped at the Portal as in rung 3.
2. **Snapshot.** With the secrets set, `version=0.0.1-SNAPSHOT` on the branch exercises the token,
   the key and a real upload, to the snapshot repository.
3. **The full path.** With the secrets set, run `release.yml` by `workflow_dispatch` with the tag
   `v0.0.1-rc.1` selected as the ref; the tag still names rung 1's commit, whose version matches it.
   **Drop the deployment at the Portal; do not publish it.** Then delete the GitHub release, the tag
   and the branch.

Repository settings worth having before then: a ruleset on the version branches (pattern `[0-9]*`:
no deletion, no force push), and one on the `v*` tags limiting who can create them, with a bypass
list, or nobody can push a release tag at all.
