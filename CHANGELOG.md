# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), with the section
names the ScalarDB family uses (Enhancements, Improvements, Bug fixes) instead of Keep a Changelog's
types. It is generated by [changie](https://changie.dev) from the files in `.changes/`; changes not
yet released are in `.changes/unreleased/`.

## [v3.20.2] - 2026-11-26

### Bug fixes

- On PostgreSQL, a duplicate key on an INSERT into a ScalarDB table no longer lets the transaction commit its other writes. PostgreSQL aborts a transaction when a statement in it fails, but after this duplicate the driver let the transaction go on, so a later `COMMIT` kept the writes before it. The transaction now fails as PostgreSQL's own does: later statements and `commit()` fail with `25P02`, as on PostgreSQL, until the application rolls back, either the whole transaction or to a savepoint set before the duplicate. Under pgjdbc's `autosave`, the transaction goes on, as it does on PostgreSQL there. The other engines are unchanged.
- In `snsql`, a meta-command such as `\dt ec.*;` now drops its trailing semicolons, as psql does. It had searched for a table named `ec.*;` and found none.
## [v3.20.1] - 2026-11-15

### Bug fixes

- The driver now works with Oracle Database 19c, tested on 19c SE2 19.3.0 with ojdbc11 23.26; CI runs the Oracle integration tests on 19c beside Oracle Free 23. On Oracle before 23 (19c, 21c), a batch of INSERTs into a decoupled table had left the old row's transaction ID, state and version under the new data row when the key had an existing metadata row, such as a tombstone; the batch now takes that metadata row over. Like 3.20.0, 3.20.1 is tested against ScalarDB 3.19.1, and ScalarDB 3.20 writes the same transaction metadata columns and states as 3.19.
- On Oracle, run the setup again after upgrading. The setup now builds the in-flight index function-based, over expressions that are NULL on a committed row, so that it holds only the rows in flight, and the driver writes its in-flight checks on those expressions. A table set up by 3.20.0 keeps working with the plain index until the setup runs again and replaces it; until then `check` reports the table as not set up, with the reason, which `--json` gives as `reason`.
- The backfill stamps a 36-character placeholder `tx_id`, as long as a transaction's, so a backfilled row keeps its length at its first write and Oracle no longer migrates it. Rows backfilled with the earlier value keep working.
- On Oracle, a READ COMMITTED read whose WHERE and ON clauses name only the table's key columns now reads each row's committed image from one derived table, with no second branch for the rows in flight and no read of the in-flight index: on an inline table, and on a decoupled table inside a transaction, where a key lookup reads the data row and its metadata row by their primary keys alone. A key lookup on an inline table costs what the plain statement costs, and an aggregate over such a predicate, such as an order's sum, runs in one round trip.
- More reads now run as written over the data tables, with the driver's in-flight checks carried in the statement, when none of their tables has a row in flight, on PostgreSQL and Oracle. Before, these read every table through its committed-rows view, which took from several times to over a thousand times the time of the same query through the database's own driver on TPC-H:
  - In autocommit at SNAPSHOT or SERIALIZABLE, a read the driver checks table by table, such as a join of five or more ScalarDB tables, as it already did inside a transaction. On PostgreSQL, TPC-H joins of six to eight tables took over 30 seconds against 20-60 ms.
  - At READ COMMITTED, in a transaction and in autocommit: a read too large to rewrite into copies, such as a join of five or more tables; a read with a subquery on a ScalarDB table that aggregates or limits its rows, a scalar subquery, a CTE or a UNION, such as TPC-H Q18 and Q20; and a read that records no rows for later writes, such as an aggregate or a read in autocommit, after a quick check in its key range where the statement gives one, otherwise in the whole table. A table found busy by the whole-table check skips that check for a second, across connections, so a busy table costs at most one extra statement a second.
  - A READ COMMITTED read with a subquery as above no longer records the rows it read, its other tables' included, for the checks of later writes in the transaction.
- On Oracle, a read the driver runs as written behind its in-flight checks answers an empty result in one statement where it neither groups nor selects DISTINCT. In autocommit such a read had run a second time, and at READ COMMITTED an empty result had fallen back to the rewritten form.
- Hibernate's `IDENTITY` keys now work on Oracle, so Spring Data JPA and Hibernate applications can insert into a ScalarDB table there. Hibernate's Oracle dialect gives the key column as `DEFAULT`, such as `INSERT INTO item (name, id) VALUES (?, DEFAULT)`, which the driver refused with `0AN01`; a one-row INSERT that gives a column as `DEFAULT` now runs as if it left that column out. A new sample, `samples/crud-jpa`, runs Spring Data JPA and Hibernate through the driver on every engine.
- On MariaDB 11.6.2 and later, where `innodb_snapshot_isolation` is on by default, a write conflict at REPEATABLE READ or SNAPSHOT (error 1020, "Record has changed since last read") now comes as 40001, so that applications retry it, rather than as HY000.
- On Oracle, a read whose ORDER BY names a position past its select list, such as `SELECT x FROM t ORDER BY 2`, fails with ORA-01785 as it does on the database. A read without anchors, such as one in autocommit, had sorted silently by a column the driver adds to the select list.
- A read of an inline table whose enclosing query names a column like the table, such as TPC-H Q9's `nation` over `FROM (SELECT n_name AS nation ... FROM nation ...)`, now runs as written once the transaction found its tables clear. The driver had taken the column for the table's whole row and read every table of the statement through its committed-rows view: on PostgreSQL, 1,035 seconds against 59 ms for Q9.
- On PostgreSQL, a read the driver runs as written behind a whole-table in-flight check, or the statement as written of a read too large to rewrite into copies, now uses the session's parallel workers. A short rewritten read earlier on the connection had left them off, so that at TPC-H scale factor 3 such reads ran 1.3 to 6.5 times the time of the database's own driver.
## [v3.20.0] - 2026-10-30

### Enhancements

- The first release of ScalarDB Native JDBC, a JDBC driver for a database that holds both ordinary tables and ScalarDB tables. The application uses the database's own SQL and transactions on both: a transaction through the driver is one native transaction, ACID across both kinds of table, and ScalarDB's transactions on the same tables keep their guarantees. The driver wraps the database's own JDBC driver, which the application supplies, and connects with `jdbc:scalardb-native:<database>:...` URLs. It is published to Maven Central as `com.scalar-labs:scalardb-native-jdbc` and runs on Java 11 or later. See `docs/getting-started.md`.
- PostgreSQL, MySQL, MariaDB and SQL Server are supported at READ COMMITTED, SNAPSHOT and SERIALIZABLE, and Oracle at READ COMMITTED and SNAPSHOT, tested against ScalarDB 3.19.1; ScalarDB 3.20 writes the same transaction metadata columns and states as 3.19. A connection starts at SNAPSHOT, ScalarDB's default. Both of ScalarDB's layouts are served, inline and decoupled transaction metadata, and an application names a table the same way in either. See `docs/transactions.md` and `docs/sql-support.md`.
- `scalardb-native-tools`, shipped as `scalardb-native-tools-<version>.zip` on the GitHub release, runs the one-time setup the driver needs on ScalarDB tables, checks it, undoes it, and adds a table to it while applications run. With `--backfill` the setup also writes the transaction metadata of imported tables, which is off by default; `backfill` runs it alone and repairs the rows ScalarDB leaves with NULL metadata, which `check` reports. See `docs/setting-up-tables.md`.
- `snsql`, a psql-like interactive shell that goes through the driver on all five databases, shipped as `scalardb-native-shell-<version>.zip` on the GitHub release. See `docs/snsql.md`.
- Every error the driver raises carries an SQLState, listed with its cause and what to do about it in `docs/errors.md`.
